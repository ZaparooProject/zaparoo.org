## Profiles and parental controls

Families and other shared-device setups can now create a [profile](/docs/features/profiles/) for each person. Every profile can inherit the device's playtime settings or use its own daily and session limits, with usage tracked against the person who launched the game. You can also require a personal profile before any media launches, leaving the device parked until someone identifies themselves.

Profiles are created and managed from the Core terminal UI. Switch from the profile list with an optional PIN, or write a profile card for instant switching. Core remembers the active profile across restarts, and selecting the shared profile returns to the device's existing global settings and data. Profile cards bypass the PIN, so treat them like keys: anyone with the card can activate that profile.

On MiSTer, profiles also get separate save files and save states automatically. Existing saves stay with the shared profile, while each personal profile starts with its own empty save directories. If you switch while a game is running, Core waits for it to stop before changing the live save data. Save separation is currently limited to MiSTer; profiles on other platforms still provide switching and individual playtime controls.

MiSTer users running [odelot's custom RetroAchievements Main](https://github.com/odelot/Main_MiSTer) can also keep a separate RetroAchievements account for each profile. First activation copies the currently visible account configuration, which can then be changed independently. The shared profile returns to the original account. These configuration files contain plaintext passwords, so Core intentionally excludes them from local and cloud backups.

Admin and member roles protect profile and settings management in the terminal UI. Paired clients can also be approved as admin or member devices. To enforce those client restrictions remotely, enable **Require encryption** under **Settings > Clients**. Profiles are designed as household parental or kiosk controls rather than operating-system account security.

## Back up settings and saves

MiSTer and MiSTeX devices can now create [portable backups](/docs/features/backups/) containing Zaparoo configuration and user data together with MiSTer settings, input mappings, saves, save states, and profile-specific save directories. Local backups are stored as ZIP files and do not require an online account.

Restores validate the backup and its contents before changing the device, create a local safety backup, and roll back if anything fails. Core restarts after a successful restore while keeping the destination device's identity, paired clients, encryption setting, and Zaparoo Online link. Backups do not include ROMs, downloaded cores, scraped artwork, or authentication credentials.

Zaparoo Warp members can also link Core to their Zaparoo Online account for cloud snapshots. Upload manually or choose a daily or weekly schedule, then browse snapshots by their source device and restore one to another compatible device. Restoring copies the snapshot without changing the source device or cloud backup.

Backup work yields to games. Most launches throttle collection and uploads, while storage-sensitive CD cores pause them until the game stops. Interrupted scheduled backups retry sooner after Core restarts instead of waiting for the next full schedule interval.

## Large-library indexing and recovery

Media indexing has been reworked to handle very large libraries without loading the existing media database into memory. Core now processes one system at a time and keeps completed systems available for search and browsing while the rest of the update continues.

Interrupted indexes keep their completed work and resume on startup. If an index repeatedly stalls at the same system, Core pauses it, keeps the cached library browsable, and adds an Inbox warning with recovery steps. Large browse requests can also show a populated folder with an unknown count instead of failing while Core repairs stale cache data in the background.

Indexing and metadata scraping now yield to gameplay. Most systems use a light throttle, optical systems use a heavier one, and 3DO, CD-i, Jaguar CD, and Saturn pause background media work completely. Linux workers also use low CPU and I/O priority.

Core can now recover automatically when it detects corruption in the rebuildable media database. It verifies the replacement, starts a full index, and preserves favorites, history, token mappings, and saved launcher overrides in the separate user database. An Inbox message reminds you to scrape artwork and metadata again. After three failed recovery attempts in one Core session, it stops and suggests checking free space or replacing the storage device instead of repeatedly rebuilding.

Apps can also list every system supported by the platform before its emulator or runtime is installed, allowing those systems to be selected for indexing while setup is still in progress.

## Smarter artwork caching

Core now keeps resized artwork caches separate for each system. A selective media update or metadata scrape only clears thumbnails for systems whose images actually changed, instead of discarding unrelated artwork. Metadata-only and no-change scrape results leave existing thumbnails alone, reducing repeated image processing and unnecessary SD-card writes.

Image requests can now use 32px and 64px resize tiers alongside the existing larger sizes. These small WebP images give clients a lightweight placeholder that is faster to decode on devices such as MiSTer while full-size cover art loads in the background.

Thumbnail writes now use atomic replacement, and Core cleans up abandoned temporary files and older cache formats automatically. If a scrape is interrupted, Core invalidates only the known affected systems when it can do so safely, falling back to a full refresh when the scope is uncertain.

## Custom gamelist bundles

Thanks to [BossRighteous](https://github.com/BossRighteous), Core can now import [per-system `gamelist.xml` bundles](/docs/features/scraping/#custom-gamelist-bundles) stored separately from your ROM folders. This keeps a curated metadata and artwork library in a separate location while leaving game storage unchanged.

Set `scraper.gamelist_xml.custom_path` to the bundle directory, with one subfolder for each system ID. Custom gamelists enrich games already in the media database and use their own directory for artwork and other assets. Regular gamelists beside the ROMs still take priority, and missing bundle images can fall back to EmulationStation-style `media/` folders in the bundle or ROM roots.

## Launch indexed games from physical discs

Core can now [identify supported physical game discs](/docs/readers/optical-drive/#launch-an-indexed-game-from-its-original-disc) and launch the matching disc image from your indexed media library. It still does not run the game directly from the disc: the disc works as a physical trigger for the copy already stored on your device.

Run a media database update after installing this release so Core can add game IDs to supported disc images. Matching works with `.chd`, `.cue`, `.gcm`, and `.iso` files for Nintendo GameCube, Sega CD/Mega CD, Neo Geo CD, PlayStation, PlayStation 2, PSP, and Sega Saturn. Compressed `.cso`, `.gcz`, and `.rvz` images are not supported for this matching.

Insert the corresponding game disc into a connected Linux optical drive and Core launches the indexed file when exactly one match is found. Existing token mappings still take priority, and Core does not guess when a disc matches zero or multiple indexed files.

MiSTer can now automatically detect optical drives exposed as `/dev/sr0`, `/dev/sr1`, and similar Linux device paths. Manual reader configuration remains available when detection is unavailable. Disc identification remains stable while a disc is inserted, avoiding unnecessary repeat scans and tolerating temporary read failures.

## RetroArch on Linux and SteamOS

Core now includes [built-in RetroArch launchers](/docs/platforms/linux/launchers/#retroarch) on generic Linux and SteamOS. These launchers map supported systems to default RetroArch cores and scan ROMs from ES-DE-style system folders, removing the need to create a custom launcher for each core.

Core checks whether the RetroArch Flatpak and required core are installed before using each launcher. Missing dependencies no longer lead to a failed automatic launch: apps can show that the launcher is unavailable and explain what is missing. You can also override the core selected for an individual launcher through its `load_path` default.

RetroArch launchers support save state, load state, menu, pause, reset, fast forward, rewind, and stop controls. Core enables these through a separate network-command config overlay instead of changing your primary RetroArch configuration.

On SteamOS, the same launchers integrate with EmuDeck's RetroArch systems while standalone EmuDeck emulators remain supported. RetroArch launches also receive Gaming Mode focus handling. Process tracking has been tightened so active-media state is cleared when the launched emulator exits without an older process clearing a newer launch.

## Native emulators on SteamOS

SteamOS can now [launch games through experimental native emulator integrations](/docs/platforms/steamos/#native-emulators), without requiring EmuDeck or RetroDECK. Supported emulators include Xenia Canary, Ryubing, shadPS4, PCSX2, Cemu, Azahar, Vita3K, RPCS3, DuckStation, PPSSPP, Dolphin, melonDS, ScummVM, Supermodel, xemu, and PrimeHack. Core checks whether each Flatpak or executable is installed before selecting it, so missing runtimes can be reported instead of producing a failed launch.

A new `launchers.preference` setting chooses an ordered fallback across launcher groups. SteamOS users can prefer `Native`, `EmuDeck`, or `RetroDECK`, while explicit token launchers, saved per-game overrides, and system defaults continue to take priority. When several launchers scan the same system, Core now merges duplicate paths while preserving the best available display metadata.

Native RetroArch launches use Zaparoo-owned low-latency configuration profiles for each system. These enable network controls while tuning video and audio latency and disabling features that conflict with the profile. Your primary RetroArch configuration remains unchanged.

Gaming Mode handling is more reliable across SteamOS, Bazzite, and ChimeraOS. Core carries the active session environment into launched apps, finds Flatpak windows more reliably, restores the previous gamescope focus after exit, and stops the active launcher when returning to the menu. Steam tracking also ignores stale process events from older launches so they cannot clear or stop a newer game.

## More reliable MiSTer console apps

Core now [coordinates MiSTer console ownership](/docs/platforms/mister/launchers/#console-launcher-rendering) between Zaparoo Frontend widgets, visible scripts, video playback, ScummVM, and other ARM apps. This fixes Core-side conflicts where starting media from Zaparoo App while Frontend was active could briefly interrupt the display, then reload Frontend instead of showing the media.

Console launchers now wait for earlier processes and their child processes to stop before taking over the display. Core restores the console and Frontend after a launcher exits, crashes, or is forcibly stopped, and ScummVM receives a graceful exit before Core falls back to terminating it. Newer compatible MiSTer Main builds can explicitly hand console ownership to Core, while stock and older builds continue using the existing fallback behavior.

:::note Frontend update required
Launching visible scripts or ARM apps while Zaparoo Frontend is active also requires a corresponding Zaparoo Frontend update. Updating Core alone does not fully resolve those conflicts.
:::

Video and ScummVM rendering can now be tuned through launcher defaults. `render_scale` supports 25%, 33%, 50%, or 100% of the current output dimensions, while `render_resolution` accepts an exact `WIDTHxHEIGHT` framebuffer size. These settings do not change the physical display output mode. Existing defaults remain unchanged: video uses one-third dimensions and ScummVM uses 640×480.

## MiSTer arcade games by hardware

MiSTer arcade games can now [appear under their specific hardware family](/docs/platforms/mister/launchers/#hardware-classification) as well as the general Arcade library. Core uses MiSTer's Arcade Database to classify CPS1, CPS2, CPS3, Irem M72 and M92, Jaleco Mega System 1, Namco System 1, IGS PGM, Sega ST-V, Sega System 16 and 18, and Taito F2 games. Unclassified titles and the complete collection remain available under Arcade as before.

This makes it possible to browse, search, or launch a random game from one arcade platform. Core checks the requested hardware system first and only falls back to the general Arcade pool when the specific system has no matching result, rather than mixing both pools together.

Neo Geo games are also indexed under both `NeoGeo` and `NeoGeoMVS`. MVS entries keep the normal games folder but use an independent MiSTer set name, allowing separate core configuration. Run a media database update after installing v2.16.0 to add the new classifications.

## Custom launchables

Thanks to work from [Grant McNaught](https://github.com/gmcnaught), [custom launchers can now create virtual systems](/docs/features/launchers/#launchables) that appear in browse and search without needing a media file. Selecting one runs its configured command, making it possible to expose tools, apps, or other launch-only entries through the same interface used for games and media. This works across Core platforms.

MiSTer users can use the same system to add ROM-less FPGA cores that are not included in Core's built-in `_Other` list. Custom entries can also override the name, category, or path of a built-in Other core while preserving its existing identity, so App visibility, naming, and artwork settings remain attached.

Launchable identities are stable across restarts and devices as long as the configured backend and ID stay the same. Entries can be grouped under Other, Console, Computer, Handheld, or Arcade. Core validates custom launcher files and ignores unsafe paths, malformed entries, duplicate IDs, and incompatible field combinations.

## Other changes

- Added [opt-in play history sync](/docs/online/#play-history-sync) for linked Zaparoo Online accounts without requiring Warp. It is off by default; first use uploads retained local history, then syncs new and updated sessions about once an hour.
- Fixed [MiSTer Neo Geo indexing](/docs/platforms/mister/launchers/#neogeo) for root-level, nested, and symlinked ROM-set folders, with safer `romsets.xml` fallback handling and clearer diagnostics.
- Fixed stale MiSTer core detection after `.rbf` files are added, removed, replaced, or changed through symlinks. Standardized unstable-nightly filenames now work as fallbacks for systems such as 3DO, while regular cores keep priority.
